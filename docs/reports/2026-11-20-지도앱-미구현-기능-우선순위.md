# 무료 API로 대형 지도앱 격차 좁히기

wayfinder에서 체감 효과가 가장 큰 미구현 기능은 **즐겨찾기·저장 목록, 길찾기 공유, 실시간 도착 정보**다. 공유, 경로 정렬, 카테고리 칩, 지도 레이어, 다른 앱으로 길안내 넘기기, 로드뷰 링크는 지금 무료 API만으로 만들 수 있다. 즐겨찾기는 기술적으로 쉽지만 카카오의 "결과 데이터 저장 금지" 조항과 부딪칠 수 있어 약관 확인이 먼저다. 대중교통 고급 기능의 진짜 병목은 개별 기능이 아니라 **ODsay 무료(Basic) 요금제의 하루 30회 한도**다([ODsay 운영정책](https://lab.odsay.com/doc/totalPolicy)). 현재 코드는 시내 길찾기 한 번에 탐색 1회와 `loadLane` 1회를 호출하므로(`packages/shared/src/transit/koreaTransit.ts`), 하루 약 15회 검색이면 한도가 끝난다. 실시간 버스 도착, 막차, 출발시각 변경은 모두 ODsay 추가 호출이나 ODsay 정류장 ID를 거쳐야 해서 이 한도를 그대로 갉아먹는다. 그래서 판정은 세 갈래다. **지금 무료로 가능한 것**은 공유·정렬·칩·레이어·앱 연계 길안내·로드뷰 링크·서울 지하철 실시간 도착이다. **조건부로 가능한 것**은 즐겨찾기(약관), 버스 실시간 도착(정류장 ID 확보), 막차(지하철 한정), 출발시각 변경(ODsay 쿼터와 요금제 제공 여부 미확인), 장소 상세의 영업시간(구글 월 1,000회 한도 안에서만)이다. **무료로는 불가능한 것**은 검색 목록의 "영업중" 필터, 버스+지하철 혼합 경로의 도착시각 기준 검색, 실시간 혼잡도다. 선결 과제는 2026-07-21에 나온 **카카오 대중교통 경로 REST API(일 1,000회 무료)**를 주 라우터로 옮기고 ODsay는 막차·시간표처럼 그것만 가진 기능에 아껴 쓰는 구조 전환이다([Kakao DevTalk 150222](https://devtalk.kakao.com/t/api-notice-on-new-kakao-map-api-features-and-free-quota-policy/150222)).

## 네이버는 장소, 카카오는 실시간 교통으로 사용자를 붙잡는다

경쟁 구도부터 보면, 2026년 8월 MAU는 **네이버지도 3,080만, 카카오맵 1,349만**이고 구글지도는 7월에 처음 1,000만을 넘었다([전자신문 2026-09-03](https://www.etnews.com/20260903000250), [CEO스코어데일리](https://m.ceoscoredaily.com/page/view/2026102615520675596)). 설문 이용률(중복응답)은 네이버 79.0%, 카카오 40.6%, 티맵 32.6%, 구글 23.7%로, 대부분의 사용자가 네이버를 기본으로 쓰면서 다른 앱을 병행한다([세계일보 2026-08-04](https://www.segye.com/newsView/20260804506965)). 네이버는 검색→길찾기→예약→리뷰를 잇는 올인원 전략으로, 카카오는 초정밀 버스·지하철과 로컬 서비스로 성장했다([전자신문 2026-05-18](https://www.etnews.com/20260518000283)). 대중교통·도보 웹앱인 wayfinder의 직접 비교 대상은 네이버의 장소 경험과 카카오의 실시간 교통이다. 구글지도는 외국인·해외여행 수요와 안드로이드 기본 탑재로 성장했다는 분석만 있고, 한국 내 기능 비교 자료는 이번 조사에 거의 없다. 구글 비교는 이 보고서에서 얇게 다룰 수밖에 없다.

사용 행태를 비율로 보여 주는 최신 공개 자료는 엠브레인의 2026년 조사(n=1,000) 하나다. 여기서 **63.9%가 여행 때 장소를 저장하고 경로를 계획**하고, **53.5%가 만날 장소를 지인과 지도를 함께 보며 정하며**, **51.3%가 저장해 둔 목록을 해당 지역에 갈 때 다시 꺼내 쓴다**([다음/엠브레인 2026-08-04](https://v.daum.net/v/20260804101528061)). 최대 불만은 오래된 장소 정보(41.6%)와 광고·협찬 리뷰(37.9%)였다(같은 출처). 네이버는 2025년 11월 탭을 발견·예약·대중교통 순으로 재편해 대중교통을 세 번째 탭으로 밀었다([바이라인네트워크 2025-11-10](https://byline.network/2025/11/10-538/)). 광고 없이 대중교통 길찾기를 첫 화면에 두는 단순한 UI가 wayfinder의 차별점이 될 여지가 여기서 생긴다.

실시간 교통은 두 회사가 2025~2026년 모두 투자한 기본기다. 카카오는 2025년 6월 수도권·부산 23개 노선의 실시간 열차 위치를 지도에 띄웠고([카카오 보도자료](https://www.kakaocorp.com/page/detail/11586)), 네이버는 2025년 5월 부산 지하철 실시간 도착을 추가했으며([비즈워치](https://news.bizwatch.co.kr/article/mobile/2025/05/08/0015)) 2026년 3월에는 운행중단·무정차 정보를 지도에 표시했다([한국경제](https://www.hankyung.com/article/2026031398711)). 다만 정확도는 보장되지 않는다. 기자 1인의 실사용 비교에서 1호선 지연 때 두 앱 모두 도착 시각에 지연을 반영하지 못했고, 카카오의 열차 위치 애니메이션만 실제와 맞았다([머니투데이 2025-07-06](https://www.mt.co.kr/tech/2025/07/06/2025070423501632966)). 체계적 측정이 아닌 사례 하나라는 점은 감안해야 한다.

**우선순위의 근거에 대한 단서:** 엠브레인 수치가 받쳐 주는 것은 저장·공유뿐이다. "실시간 도착 vs 막차 vs 혼잡도" 중 무엇을 더 원하는지 보여 주는 설문이나 사용 통계는 찾지 못했다. 아래 순위는 (1) 사용자 가치 근거의 강도, (2) 무료 API로 실현 가능한지, (3) ODsay 30회 한도에 의존하는지, (4) 구현 규모를 기준으로 한 판단이다.

## 한 장으로 보는 판정: 후보 열네 개 중 일곱 개는 지금 바로 무료로 된다

현재 상태는 2026-11-20 코드 스냅샷 기준이다. 11-18 기능 검토(`docs/plans/2026-11-18-feature-review.md`)에서 P2로 계획만 잡힌 항목(카테고리 칩, 교통정보 레이어, 출발시각 변경)과 아예 계획에 없던 항목(즐겨찾기, 공유 버튼, 실시간 도착, 막차, 앱 연계 길안내)을 구분해 표기했다. 맨 윗줄의 라우터 전환은 기능이 아니라 선결 조건이라 개수에서 뺐다.

| 기능 | 현재 상태 | 사용자 가치 근거 | 무료 구현 판정 | 우선순위 |
|---|---|---|---|---|
| 대중교통 주 라우터를 카카오로 전환 + 프록시 캐시 | ODsay 직접 호출, 검색당 2회 | 모든 대중교통 기능의 전제 | 가능(일 1,000회, 프록시 필수) | **선결** |
| 즐겨찾기·저장 목록 | 없음(최근 검색만 `src/search/recentSearches.ts`) | 63.9%·51.3% | 기술적으로 가능, **약관 리스크** | 1 |
| 길찾기·장소 공유 버튼 | URL 상태는 있음(`src/route/routeUrl.ts`), 버튼 없음 | 53.5% | 가능(카카오톡 공유 일 30,000회) | 1 |

| 서울 지하철 실시간 도착 | 없음 | 경쟁사 기본기 | 가능(일 1,000회, 서울 구간만) | 2 |
| 버스 실시간 도착 | 없음 | 카카오의 핵심 차별점 | API는 무료, **정류장 ID 매핑이 ODsay 의존** | 3 |

로드뷰는 전용 라우트(`apps/mobile/app/roadview/[id].tsx`)가 있지만, 키가 있는 실 모드에서도 "카카오 로드뷰 (키 연동)" 문구만 렌더하고 SDK 로드뷰는 아직 마운트하지 않는다(`apps/mobile/src/screens/RoadviewScreen.tsx`). 카카오 `map.kakao.com/link/roadview/위도,경도` 링크로 바꾸면 쿼터 소모 없이 바로 동작한다([Kakao Maps Web 가이드](https://apis.map.kakao.com/web/guide/)). SDK 임베드는 `getNearestPanoId` 호출마다 쿼터가 차감되므로 사용자가 누를 때만 불러야 한다([DevTalk 150932](https://devtalk.kakao.com/t/web-sdk/150932)).

## 대중교통: 실시간 도착은 무료지만, 막차와 출발시각은 ODsay 한도에 묶인다

**한도 문제의 해법은 라우터 교체다.** 카카오 대중교통 경로 조회(`GET dapi.kakao.com/v2/routing/publictraffic`)는 2026-07-21 출시됐고 **일 1,000회 무료, 초과 시 건당 10원**이다. 단, 무료 쿼터는 개발자 계정에서 카카오맵을 처음 활성화한 앱 하나에만 붙는다([Kakao 쿼터](https://developers.kakao.com/docs/latest/ko/getting-started/quota)). 응답에는 단계별 폴리라인(`steps[].path.points`), 요금, 환승 수가 들어 있어 지금의 `loadLane` 추가 호출이 필요 없을 수 있다. 대신 출발시각·정렬·실시간 파라미터가 없고, 정류장은 이름만 준다([Kakao Developers REST API](https://developers.kakao.com/docs/ko/kakaomap/rest-api)). 이번 조사의 프로브에서는 키 없는 요청에 CORS 헤더가 없었으므로 프록시(`services/proxy`)를 거쳐야 하고, 그래야 REST 키도 숨길 수 있다. ODsay를 유료로 올리는 길도 있다. Flex 요금제는 건당 25원(부가세 별도)이라 하루 1,000회 검색이면 최소 약 5만 원, 월 150만 원 이상이 든다([ODsay 운영정책](https://lab.odsay.com/doc/totalPolicy)). 참고로 현재 앱이 보는 429 "Daily quota exceeded"가 이 30회 한도 때문이라는 판단은 추론이다. ODsay 문서에는 한도 초과 시 상태 코드가 명시돼 있지 않다. 출시 직후라 카카오 API의 "code -10" 같은 DevTalk 문의 제목이 보이는 점도 초기 위험 신호로 기억해 둘 만하다([DevTalk 150841](https://devtalk.kakao.com/t/api-rest-code-10/150841)).

**실시간 도착 데이터는 전부 공공 API로 무료다.** 서울 지하철은 역 이름으로 조회하는 swopenAPI를 쓴다. **일 1,000회** 한도이고, 활용사례를 등록하면 늘릴 수 있으며, **서울시 밖 구간은 제공하지 않는다**([서울 열린데이터광장 이용안내](https://data.seoul.go.kr/together/guide/useGuide.do), [OA-12764](https://data.seoul.go.kr/dataList/OA-12764/F/1/datasetView.do)). 버스는 서울(`ws.bus.go.kr`, 개발 계정 일 1,000회)([data.go.kr 15000314](https://www.data.go.kr/data/15000314/openapi.do)), 경기(GBIS v2, 일 1,000회)([data.go.kr 15080346](https://www.data.go.kr/data/15080346/openapi.do)), 부산(자체 BIMS), 그 밖의 지역(TAGO, 일 10,000회)([data.go.kr 15098530](https://www.data.go.kr/data/15098530/openapi.do))으로 나눠 호출하면 전국 버스를 덮는다. 서울 밖 지하철(인천·부산 등)의 실시간 소스는 이번 조사에서 찾지 못했다. 서울 API 두 개는 이번 조사의 직접 요청에서 `http://`만 응답해서 HTTPS 웹앱에서는 혼합 콘텐츠로 막힌다. 이 역시 프록시가 필요하고, 정류장별 15~30초 캐시면 키 하나로 가벼운 사용량은 버틸 수 있다. 카카오는 실시간 정보를 오픈 API로 제공하지 않는다고 2026년 10월 직접 답했고([Kakao DevTalk](https://devtalk.kakao.com/t/api/151941)), ODsay 자체 실시간 엔드포인트는 레퍼런스 페이지에서 주석 처리돼 사실상 사라졌다([ODsay API Reference](https://lab.odsay.com/guide/releaseReference)).

**숨은 의존성은 정류장 ID다.** 공공 버스 API는 ODsay의 `arsID`(서울, 하이픈 제거)나 `localStationID`(경기·TAGO·부산)로 조회하라고 ODsay가 안내한다([ODsay 실시간 연동 가이드](https://lab.odsay.com/guide/guide)). 카카오 라우터로 옮기면 정류장 이름만 남으므로 ID를 얻으려면 ODsay `searchStation`을 다시 불러야 하고, 그러면 30회 한도로 되돌아간다. 현재 정규화 코드는 ODsay 응답에서 정류장 ID를 저장하지 않는다(`packages/shared/src`, `apps/mobile/src`, `services/proxy/src`를 대소문자 구분 없이 검색해도 `arsID`·`localStationID`·`stationID` 참조가 없다). ODsay 경로 응답에 탑승 정류장 ID가 이미 들어 있는지는 이번 조사에서 확인하지 못했다. 그래서 **서울 지하철 실시간 도착(역 이름만으로 조회)을 먼저** 붙이고, 버스는 정류장 ID 확보 방법이 정해진 뒤로 미루는 순서가 맞다.

**막차와 출발시각은 지하철에 한해, 조건부로 된다.** 현재 쓰는 `searchPubTransPathT`에는 시간 파라미터가 없다. 시간 기반 경로는 `maasRP`(`SearchTime` 필수, 출발시각 기준)와 `subwayPathSchedule`(출발 기준·도착 기준·첫차·막차 4개 모드, 지하철 전용)에만 있다([ODsay API Reference](https://lab.odsay.com/guide/releaseReference)). 가장 싼 막차 경고는 22시 이후 검색에서만 지하철 구간에 `subwayPathSchedule` MODE=4를 호출해 "운행 종료" 배지를 다는 방식이다. 이 두 API를 무료 Basic 요금제에서 쓸 수 있는지는 문서에 나오지 않는다. TMAP 대중교통 API의 `searchDttm`은 구간별 운행 여부(`service` 1/0)를 직접 알려 주지만([TMAP 대중교통 API](https://transit.tmapmobility.com/docs/routes)) 현재 무료 한도를 확인하지 못했다. 버스+지하철 혼합 경로를 도착시각 기준으로 찾는 무료 API는 없다.

**경로 비교는 추가 호출 없이 된다.** 대안 경로 목록은 이미 렌더링된다(`apps/mobile/src/screens/RouteResultScreen.tsx`). ODsay의 `totalTime`, `totalWalk`, `busTransitCount + subwayTransitCount`로 최소시간·최소도보·최소환승 정렬 탭을 클라이언트에서 만들 수 있다. 카카오 응답도 `totalTime`, `transfers`, `type`(BUS/SUBWAY/BUS_AND_SUBWAY)을 주므로 라우터를 바꿔도 최소시간·최소환승 정렬과 수단 필터는 그대로 된다. 다만 카카오 응답에 총 도보 거리 필드가 있는지는 확인하지 못해서, 최소도보 정렬은 단계별 도보 구간을 합산해야 할 수 있다. 지하철/버스 필터도 재검색 대신 이미 받은 결과를 거르는 편이 쿼터를 아낀다. 혼잡도는 실시간 무료 소스가 없다. 서울교통공사 1~8호선 30분 단위 통계(분기 갱신)로 "평소 혼잡" 힌트를 주는 것이 무료로 할 수 있는 최대치다([data.go.kr 15071311](https://www.data.go.kr/data/15071311/fileData.do)).

## 장소: 칩과 저장은 쉽고, 영업시간은 구글 유료 영역이다

**카테고리 칩과 "이 지역 재검색"은 무료 쿼터 안에서 완성된다.** Kakao Local `search/category`는 카페(CE7), 편의점(CS2), 음식점(FD6), 주차장(PK6), 주유소·충전소(OL7), 병원(HP8), 약국(PM9), 은행(BK9), 숙박(AD5), 지하철역(SW8) 등 공식 그룹코드 18개를 지원하고, `radius`(최대 20km)나 `rect`로 범위를 정한다. 키워드·카테고리 검색은 각각 **일 100,000회**다([Kakao Local 가이드](http://developers.kakao.com/docs/ko/local/dev-guide), [Kakao 쿼터](https://developers.kakao.com/docs/ko/getting-started/quota)). JS SDK의 `services.Places`에도 `useMapBounds` 옵션이 있어, 사용자가 지도를 움직인 뒤 버튼을 눌렀을 때만 현재 화면 범위로 재검색하면 된다([Kakao Maps Web 문서](https://apis.map.kakao.com/web/documentation/)). 제약은 한 쿼리당 결과 **최대 45건**이라는 점이다. 프록시 정규화가 이미 `category_group_code`를 다루므로(`services/proxy/src/normalize/kakaoPlace.ts`) 추가 작업이 작다. 그룹코드에 없는 세분류(화장실, 전기차충전소만 따로 등)는 키워드 검색으로 대체한다.

**영업시간과 "영업중" 배지는 무료로 재현할 수 없다.** Kakao Local 응답에는 영업시간·메뉴·사진·평점 필드가 없고 전화번호(`phone`)만 있다([Kakao Local 가이드](http://developers.kakao.com/docs/ko/local/dev-guide)). 네이버 지역검색은 `telephone`조차 더 이상 채우지 않고 결과도 최대 5건이다([NAVER API HUB 지역검색](https://api.ncloud-docs.com/docs/naver-api-hub-search-local)). 남는 길은 Google Places (New)인데, `regularOpeningHours`·`currentOpeningHours`·`rating`은 **Enterprise SKU로 월 1,000회 무료, 이후 1,000회당 $20**이다. `reviews`를 field mask에 넣으면 Enterprise+Atmosphere($25)로 올라가고, 사진 이미지는 별도 Photos SKU(월 1,000회)가 든다([Place Data Fields](https://developers.google.com/maps/documentation/places/web-service/data-fields), [GMP Pricing](https://developers.google.com/maps/billing-and-pricing/pricing)). 검색 결과 15건마다 영업 여부를 붙이면 무료분이 며칠 안에 사라진다. 따라서 현재처럼 상세 화면에서 사용자가 탭할 때만 부르는 lazy 구글 탭(`services/proxy/src/index.ts`의 `/v1/places/:id/google`)이 올바른 설계다. 이 호출의 field mask는 이미 `id,rating,userRatingCount,reviews`라서(`services/proxy/src/routes/place-google.ts`) 최고 등급인 Enterprise+Atmosphere로 과금되고 있다. 같은 마스크에 `currentOpeningHours`를 더하면 추가 호출 없이 상세 화면에 영업시간과 "지금 영업중"을 보여 줄 수 있다. 반대로 목록 단계의 "영업중" 필터 칩은 포기하는 것이 맞다. 한국 내 구글 장소 데이터에 영업시간이 얼마나 채워져 있는지는 근거를 찾지 못했다. 메뉴는 세 API 모두 필드가 없으므로 카카오 `place_url`로 딥링크하는 것이 전부다.

**즐겨찾기는 수요가 가장 확실하지만 약관 리스크가 미해결이다.** 네이버는 2022년에 첫 화면 '저장' 탭을 만들고 5,000곳 저장과 리스트 공유를 넣었다([세계일보 2022-12-13](https://www.segye.com/newsView/20221213515529)). 계정 없이 localStorage에 저장하는 것은 기술적으로 쉽고, 최근 검색에 이미 같은 방식을 쓰고 있다. 문제는 카카오가 "로컬 API 결과 데이터를 별도로 저장하여 사용하는 것은 허용하지 않는다"고 명시한다는 점이다([Kakao devtalk FAQ](https://devtalk.kakao.com/t/faq-api/125610)). 구글처럼 ID만 저장하고 열 때 다시 조회하면 안전하겠지만, Kakao Local에는 ID로 조회하는 API가 없다. 결국 이름과 좌표를 최소한으로 저장해야 하고, 사용자 브라우저에 두는 것이 금지 조항에 해당하는지는 공식 답변이 없다. 출시 전에 DevTalk에 문의하고, 그동안은 사용자가 직접 붙인 이름·메모와 좌표만 저장하는 최소 설계로 가는 편이 안전하다. 기기 간 이동은 목록을 URL에 인코딩하거나 JSON으로 내보내는 방식으로 계정 없이 대체할 수 있다.

## 지도 UX: 공유와 레이어는 하루치 작업이고, 회전과 다크 지도는 SDK가 막는다

**공유는 이미 절반이 돼 있다.** 경로 상태가 `?o=&d=&w=&mode=` 쿼리로 URL에 담겨 있으므로(`apps/mobile/src/route/routeUrl.ts`) 링크 자체는 존재하고 버튼만 없다. 모바일에서는 `navigator.share`를 먼저 쓴다. 이 API는 HTTPS와 사용자 클릭이 필요하고 MDN 기준 아직 Baseline이 아니므로 `canShare`로 감지해야 한다([MDN Navigator.share](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share)). 그다음으로 카카오톡 공유 버튼을 둔다. `Kakao.Share.sendDefault`의 '위치'·'피드' 템플릿을 쓰면 되고, 요구사항은 JS 키와 도메인·제품 링크 등록뿐이고 가이드에 로그인 요건이 없으며, **일 30,000회 무료**다([카카오톡 공유 JS 가이드](https://developers.kakao.com/docs/ko/kakaotalk-share/js-link), [Kakao 쿼터](https://developers.kakao.com/docs/ko/getting-started/quota)). 마지막 폴백은 링크 복사다. 카카오톡 인앱 브라우저에서 `navigator.share`가 동작하는지는 확인하지 못했으므로 복사 폴백을 빼면 안 된다. 카카오의 친구위치 기능이 감시 우려로 논란이 됐던 점을 보면([뉴시스 2025-11-17](https://www.newsis.com/view/NISX20251117_0003406094)), 실시간 위치 공유가 아니라 일회성 링크 공유에서 멈추는 것이 맞다.

**"다른 앱으로 길안내"는 웹앱의 가장 큰 구조적 공백을 무료로 메운다.** 네이티브용 턴바이턴 화면은 있지만 웹 빌드에서는 비활성 안내만 렌더한다(`apps/mobile/src/screens/NavScreen.web.tsx`). 웹 사용자가 실제 안내와 승하차 알림을 받으려면 그 순간을 대형 앱에 넘겨야 한다. 카카오맵은 `kakaomap://route?sp=위도,경도&ep=위도,경도&by=publictransit|foot`이고, 모바일 웹 폴백은 `m.map.kakao.com/scheme/`다. 좌표는 **위도,경도 순**이고 대중교통은 경유지를 받지 않는다([KakaoMap URL Scheme](https://apis.map.kakao.com/ios_v2/docs/getting-started/urlscheme/)). 이 폴백 경로에서 대중교통이 자동차 탭으로 열리던 버그는 2026년 6월 5일 수정이 완료됐다고 카카오가 답했다([DevTalk 149792](https://devtalk.kakao.com/t/url-scheme/149792)). 네이버는 `nmap://route/public?...&appname=` 형식이고 `appname`이 필수다. 안드로이드는 `intent://`, iOS는 시간차 리다이렉트로 앱 미설치에 대비한다([NCloud Maps URL Scheme](https://guide.ncloud-docs.com/docs/maps-url-scheme)). 다만 이 네이버 문서에는 `stale` 표시가 붙어 있어 구현 전에 최신 판을 다시 확인해야 한다. 데스크톱에서는 스킴 없이 `map.kakao.com/link/by/traffic/...` 웹 링크면 충분하다([Kakao Maps Web 가이드](https://apis.map.kakao.com/web/guide/)).

**레이어는 SDK 한 줄짜리다.** 웹 SDK는 기본 타입(일반·스카이뷰·하이브리드)을 `setMapTypeId`로, 오버레이(교통정보 `TRAFFIC`, 자전거 `BICYCLE`, 지형도 `TERRAIN`, 지적편집도 `USE_DISTRICT`, 로드뷰 도로)를 `addOverlayMapTypeId`로 켠다([Kakao Maps Web 문서](https://apis.map.kakao.com/web/documentation/)). 자바스크립트 SDK 쿼터는 일 300,000회다([Kakao 쿼터](https://developers.kakao.com/docs/ko/getting-started/quota)). 세 가지는 미리 알아 둬야 한다. 교통정보 타일의 갱신 주기는 문서에 없다. 지적편집도는 "참고 이외의 용도로 사용할 수 없다"는 고지를 붙여야 한다. 카카오맵 앱의 CCTV·대기질·초정밀 버스 레이어에는 웹 SDK 상수가 없어 재현할 수 없다. MapLibre 폴백 지도에서는 이 레이어들이 전부 없으므로 메뉴를 숨겨야 한다.

**SDK가 막는 것도 분명하다.** 카카오 웹 SDK 문서 전체를 검색해도 지도 회전·방위 API는 없다. 회전 관련 항목은 로드뷰 시점 옵션뿐이다. 따라서 진행 방향이 위로 오는 지도는 불가능하다. 지도는 북쪽 고정으로 두고, 내 위치 마커만 DeviceOrientation 값으로 돌리는 것이 가능한 최선이다. 지도 스타일 API도 없어서 다크 모드 지도는 스카이뷰로 대신하는 것 말고는 방법이 없다. 길게 누르기도 기본 이벤트가 아니다. 데스크톱은 `rightclick`, 터치는 약 500ms 타이머에 `coordsFromContainerPoint`와 `coord2Address`를 조합해 "여기를 출발지/도착지로" 시트를 직접 만들어야 한다(같은 문서). 카카오 로고를 오버레이로 가리는 것은 금지라서, 바텀시트 위로 `setCopyrightPosition`을 옮겨야 한다([DevTalk 150932](https://devtalk.kakao.com/t/web-sdk/150932)).

## 결론

이번 조사로 질문의 틀이 바뀌었다. "어떤 기능이 없나"보다 "어떤 쿼터가 어떤 기능을 묶고 있나"가 우선순위를 결정한다. 사용자 가치가 실측으로 확인된 저장·공유는 호출 비용이 거의 0이고, 경쟁사의 기본기가 된 실시간 지하철 도착도 공공 API로 무료다. 반면 실시간 버스, 막차, 출발시각은 하나같이 ODsay라는 일 30회짜리 병목을 통과해야 한다. 그래서 가장 레버리지가 큰 작업은 눈에 보이는 기능이 아니라 라우터를 카카오로 옮기고 프록시 캐시를 까는 일이다. 이 작업을 하면 ODsay 30회를 막차·시간표·정류장 ID 조회처럼 대체재가 없는 곳에만 쓸 수 있다. 다만 카카오 라우터는 정류장 ID를 주지 않으므로 실시간 버스와 정면으로 충돌한다. 라우터를 옮기기 전에 ODsay 경로 응답의 정류장 ID 필드를 실제로 확인하는 것이 다음 검증 순서다.

전략적으로 wayfinder가 이길 수 있는 축은 네이버·카카오와의 기능 동등성이 아니다. 대형 앱이 발견·예약·광고 쪽으로 무게를 옮기면서 생긴 "광고 없는, 대중교통 우선, 링크로 바로 열리는" 영역이 그 축이다. 영업시간·리뷰처럼 데이터 독점이 필요한 영역은 구글 lazy 탭과 카카오 상세 링크로 넘기고, 턴바이턴 안내는 앱 연계로 넘기는 편이 소형 웹앱에 맞는 분업이다. 열린 리스크는 두 가지다. 즐겨찾기 저장에 관한 카카오 약관 해석은 출시 전에 공식 답변으로 닫아야 한다. 카카오 무료 쿼터가 계정당 첫 앱에만 붙으므로 스테이징과 프로덕션을 별도 앱으로 나누는 순간 한쪽은 유료가 된다는 점도 운영 설계에 반영해야 한다.
